What it is

The public surface is intentionally small. Each module does one job. Third-party types stay private, and text or binary data that crosses a DLL / .so boundary travels as suite types, never as a std::string by value.

The suite is split on purpose: link only what you use. Base does not implement Buffer, Crypto or Network — every module lives in its own repository with its own releases, documentation and pinned dependencies.

Tools

StormByte BuildMaster

A short, declarative CMake DSL for vendoring CMake and Meson projects without the usual third-party spaghetti. Declare components and edges in any order; BuildMaster materializes stages, IMPORTED targets and one shared install prefix at the end of configure — static archives, plugin packs, whole-archive linking and per-component toolchains included.

buildmaster_component(mylib "My Library"
	"${CMAKE_SOURCE_DIR}/thirdparty/mylib/src"
	"ENABLE_FOO=ON;WITH_TESTS=OFF" shared mylib "ALIAS=My::Lib")
buildmaster_component(mytool "My Tool"
	"${CMAKE_SOURCE_DIR}/thirdparty/mytool/src" "" executable mytool)
buildmaster_link(mytool mylib)

target_link_libraries(MyApp PRIVATE My::Lib)

Design principles

  • Split on purpose. Link only what you use; every module has its own repository and releases.
  • Inherit, do not wrap. Vendor types (Crypto++, FFmpeg, sockets, SQL clients) never appear in public headers.
  • Typed failures. Expected and Fault with stable domains such as StormByte.Crypto.
  • DLL-safe boundaries. Text and bytes cross shared-library boundaries as suite types.
  • Cross-platform. Linux, Windows and macOS with GCC, Clang and clang-cl.
  • Dual licensed. LGPL v3 or later, or a commercial license from the copyright holder. BuildMaster is MIT.

Get started

Needs a C++26 compiler and CMake 3.28 or newer. Each module's README lists its exact dependencies and pins.

git clone https://github.com/StormByte-Suite/StormByte.git
cd StormByte
cmake -S . -B build
cmake --build build

Headers live under StormByte/…; the namespace root is StormByte. Shared vs static follows BUILD_SHARED_LIBS. Issues and pull requests go to the module they belong to.
